# Accounts and Nicknames Implementation Plan (stage 2)

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Players can register, sign in, edit their profile and sign out. Guests play under a claimed nickname. Nicknames are unique across accounts and online guests, and accounts win. Only signed-in players can create rooms.

**Architecture:** The server opens one SQLite database through Kysely, using better-auth's `NodeSqliteDialect` over the built-in `node:sqlite`. better-auth runs on that database and is mounted at `/api/auth/*splat`; its schema migrates on start. A pure `NicknameRegistry` on the server tracks who holds which nickname online. The socket gateway fills the registry from the session cookie (accounts) or from a new `claimNickname` event (guests). better-auth user hooks tell the registry when an account takes a name, and the registry revokes it from any guest holding it. On the client, a small auth API wraps `better-auth/client`, and the zustand store gains account state. React dialogs cover sign-in, register, profile and the "nickname no longer available" notice.

**Tech Stack:** better-auth 1.7.15 (username plugin), `@better-auth/kysely-adapter` 1.7.15 (its `node-sqlite-dialect` export), kysely 0.29, `node:sqlite` (Node 24), zod 4, Express 5, Socket.io 4, React 19, zustand, Radix Dialog, Vitest.

**Spec:** `docs/superpowers/specs/2026-11-03-levels-and-accounts-design.md` (sections Accounts, Nicknames, Storage layer, Menu changes, the permissions table, and "Decisions settled after review"). Stage 2 of its build order. Levels in the database, the level store and My levels belong to stages 3 and 4, not here.

## Global Constraints

- Code in English. Every player-facing string goes through i18n with both `es` and `en`; `en.ts` is typed against `es.ts`.
- Nickname rules are `parseNickname`'s: trimmed, 1..12 code points, no C0/C1 control characters. Accounts and guests share them.
- Uniqueness key: `nickname.trim().normalize('NFKC').toLowerCase()`. Store the name as typed (better-auth `displayUsername`) and the key (`username`).
- Reserved nickname: `BulletsNdGuns` (any case). Neither guests nor accounts may take it.
- No email verification, no forgot password, no email change, no OAuth.
- Every permission is checked on the server; the client only hides buttons.
- Secrets and config come from env: `BETTER_AUTH_SECRET`, `BETTER_AUTH_URL`, `DATABASE_PATH`, `TRUSTED_ORIGINS`. The dev defaults are for local runs only, and production refuses to start without a secret.
- Storage specifics (Kysely, SQL, `node:sqlite`) stay inside `packages/server/src/db/` and `packages/server/src/auth/`. Rooms, the gateway and the registry see only interfaces.
- Tests use an in-memory database (`databasePath: ':memory:'`).
- Untrusted input (socket payloads, level data, env config) is validated with Zod schemas (zod 4), wrapped in `parse*` functions that return `null` instead of throwing (user's request; Task 1 sets the pattern).
- Commit style: `feat(server): ...`, `feat(client): ...`, `feat(shared): ...`, `docs: ...`. Every commit message ends with `Co-Authored-By: Claude Opus 5.5 <noreply@anthropic.com>`.
- Pass better-auth options inline in the `betterAuth({...})` call (or with `satisfies`). A separately declared options object loses the username plugin's types (the spike showed `username` missing from the `signUpEmail` body type).

## Review Focus

1. **Two guests claim the same name at once** while the registry awaits the account lookup. Exactly one gets it; the registry re-checks after the await. (Test in Task 4.)
2. **Names that differ only in case or width** (`ANA`, `ana`, fullwidth `Ａｎａ`) are one name everywhere: guest against guest, guest against account, account against account. (Tests in Tasks 2, 3 and 4.)
3. **A registration whose `displayUsername` doesn't match its `username`** (shows "Admin" while holding the key "x") is refused, so nobody can display a name they don't own. (Test in Task 3.)
4. **An account takes a guest's name mid-match.** The match keeps the guest's old name in its nicknames, the guest gets `nicknameRevoked`, and their next `joinRoom` is refused with `noNickname` until they claim a new name. (Test in Task 5.)
5. **A socket with a forged or expired session cookie** connects as a guest. It never errors or crashes the server, and it can't create rooms. (Test in Task 5.)

**Interfaces:**
- Produces, exported from `@bng/shared`: `nicknameSchema`, `roomNameSchema`, `createRoomSchema`, `joinRoomSchema`, `inputFrameSchema`, `positionSchema` and `levelDataSchema`.
  - `parseNickname`, `parseRoomName`, `parseCreateRoom`, `parseJoinRoom`, `parseInput` and `parseLevelData` become one-liners: `schema.safeParse(raw)`, giving `data` or `null`.
  - Request types are inferred from the schemas (`z.infer<typeof createRoomSchema>`), except where an existing interface is exported. In that case keep the interface and type the schema with `satisfies z.ZodType<Interface>`, so the two can't drift.
- Later tasks write new validation as Zod schemas in the same style: `claimNicknameSchema` (Task 5) and the server's env schema (Task 3).

Rules that must survive the move:
- **Labels** (`nicknameSchema`, `roomNameSchema`): `z.string().trim()`, then a `refine` counting code points (`[...s].length`) in 1..max and refusing C0/C1 control characters. Zod's `.min()` and `.max()` count UTF-16 units, so they would count an emoji as two.
- **Objects:** default `z.object` strips unknown keys, which keeps the "fresh object without extra fields" tests passing.
- **`inputFrameSchema`:** `seq` is `z.int().min(1)` and `level` is `z.int().min(0)`; `z.int()` already means a safe integer. The four flags are `z.boolean()`.
- **`levelDataSchema`:**
  - `cols` is `z.literal(LEVEL_COLS)` and `rows` is `z.literal(LEVEL_ROWS)`.
  - `tiles` is exactly `LEVEL_COLS * LEVEL_ROWS` integers in 0..`TILE_KINDS`.
  - Spawns and the portal are `positionSchema.nullable()`.
  - `coins` and `ammo` have at most `MAX_PICKUPS_PER_KIND` positions.
  - `positionSchema` holds finite numbers within the bounds plus the margin.
  - **Array lengths are checked before items are parsed**, so a huge array is refused without walking it. Use `z.array(z.unknown()).max(n).pipe(z.array(item))`, or the same with `.length(n)` for tiles.
- `LevelData`, `PlayableLevelData` and `Vec2` stay hand-written interfaces with `satisfies` checks against the schemas.

### Task 4: Nickname registry

**Files:**
- Create: `packages/server/src/nicknames/nickname-registry.ts`
- Test: `packages/server/test/nickname-registry.test.ts`

**Interfaces:**
- Consumes: `AccountDirectory` (Task 3), and `parseNickname`, `nicknameKey`, `isReservedNickname` (Task 2).
- Produces:

```ts
export type ClaimResult = { ok: true; nickname: string } | { ok: false; error: 'invalid' | 'taken' };
export interface Revoked { socketId: string; nickname: string }
export class NicknameRegistry {
  constructor(accounts: AccountDirectory);
  /** Guest claim; replaces this socket's previous guest claim on success. */
  claimGuest(socketId: string, raw: unknown): Promise<ClaimResult>;
  /** A socket that belongs to an account; its nickname comes from the session. */
  connectAccount(socketId: string, accountId: string, nickname: string): void;
  /** An account registered or renamed: its sockets take the new name, guests holding it lose it. */
  accountNicknameChanged(accountId: string, nickname: string): Revoked[];
  release(socketId: string): void;
  nicknameOf(socketId: string): string | null;
  accountOf(socketId: string): string | null;
}
```

Rules:
- `claimGuest` returns `invalid` when `parseNickname` fails.
- It returns `taken` when the name is reserved, when another socket (guest or account) online holds the key, or when `accounts.isNicknameRegistered` says so. A socket re-claiming its own key gets `ok`.
- After awaiting the directory, re-check the online holders before recording the claim (Review Focus 1).
- A revoked guest has no nickname afterwards (`nicknameOf` returns null).

Gateway rules:
- `attachSocketGateway(io, rooms, { registry, sessionAccount })`.
- An `io.use` middleware awaits `sessionAccount(socket.request.headers)` and stores the result in `socket.data.account`. A null result means a guest, never an error.
- On connection, an account socket calls `registry.connectAccount`.
- `claimNickname` is rate-limited with the room actions. An account socket gets `{ ok: false, error: 'invalid' }`, because accounts rename through the profile.
- `createRoom`: a socket without an account gets `signInRequired`; otherwise `rooms.create(socket.id, name, registry.nicknameOf(socket.id))`.
- `joinRoom`: with no nickname, the result is `noNickname`.
- `disconnect` calls `registry.release` as well as leaving its room.
- `startServer`'s `nicknameChanged` calls `registry.accountNicknameChanged` and emits `nicknameRevoked(nickname)` to each revoked socket. The room a revoked guest is in keeps its nickname.

Client rules:
- `openRooms`: with an account, go straight to `'rooms'`. Otherwise, with a valid `parseNickname(nickname)`, call `actions.claimNickname`. On ok, go to `'rooms'`; on failure, set `nicknameError` and stay put.

```ts
export type AuthError =
  | 'emailTaken' | 'emailInvalid' | 'nicknameTaken' | 'nicknameInvalid'
  | 'passwordTooShort' | 'passwordTooLong' | 'wrongCredentials' | 'wrongPassword' | 'unknown';
export type AuthResult = { ok: true } | { ok: false; error: AuthError };
export function toAuthError(code: string | undefined): AuthError;
export interface AuthApi {
  session(): Promise<Account | null>;
  register(email: string, nickname: string, password: string): Promise<AuthResult>;
  signIn(email: string, password: string): Promise<AuthResult>;
  signOut(): Promise<AuthResult>;
  rename(nickname: string): Promise<AuthResult>;
  changePassword(current: string, next: string): Promise<AuthResult>;
}
export function createAuthApi(): AuthApi; // createAuthClient from 'better-auth/client' + usernameClient()
```

`toAuthError` mapping:

| Code | AuthError |
|---|---|
| `USER_ALREADY_EXISTS`, `USER_ALREADY_EXISTS_USE_ANOTHER_EMAIL` | `emailTaken` |
| `INVALID_EMAIL` | `emailInvalid` |
| `USERNAME_IS_ALREADY_TAKEN` | `nicknameTaken` |
| `INVALID_USERNAME`, `USERNAME_TOO_SHORT`, `USERNAME_TOO_LONG`, `INVALID_DISPLAY_USERNAME` | `nicknameInvalid` |
| `PASSWORD_TOO_SHORT` | `passwordTooShort` |
| `PASSWORD_TOO_LONG` | `passwordTooLong` |
| `INVALID_EMAIL_OR_PASSWORD` | `wrongCredentials` |
| `INVALID_PASSWORD` | `wrongPassword` |
| anything else, `undefined` included | `unknown` |

`register` sends `name`, `username` and `displayUsername`, all equal to the trimmed nickname. `rename` sends `username` and `displayUsername`.

Store additions:
- State: `authPending: boolean`, `authError: AuthError | null`, `nicknameRevoked: string | null`.
- `UiActions` adds `auth: AuthApi` and `reload(): void`.
- Methods:
  - `setAccount(account: Account | null)`.
  - `register(email, nickname, password)`, `signIn(email, password)`, `signOut()`: on success they call `actions.reload()`. Reloading reconnects the socket with the new cookie (spec: "the client reconnects its socket"; a reconnect already reloads the page in `main.ts`).
  - `renameAccount(nickname)`: on success it sets `account.nickname`, with no reload.
  - `changePassword(current, next)`.
  - Each sets `authPending` while running and `authError` on failure, and returns `Promise<boolean>` (`true` on success), so dialogs can close.
  - `clearAuthError()`.
  - `revokeNickname(nickname)`: ignored while a `register` for the same `nicknameKey` is pending. That is the same person, per the spec's "Decisions settled after review". Otherwise it sets `nicknameRevoked`.
  - `reclaimNickname()`: claims the current nickname field. On ok it clears `nicknameRevoked` and keeps the screen. On failure it sets `nicknameError`.

- In the first `onConnect`, await it, call `setAccount`, then move on to `'loading'`.
